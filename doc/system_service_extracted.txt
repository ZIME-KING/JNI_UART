
一、架构变更说明在原有 JNI 与 Java SDK 之间新增 SystemService 层，完整通信链路调整如下：MCU ↕ 串口 (/dev/ttyS7)libserial.so（C++ Native 层） ↕ JNIMcuSystemService（Android 系统级服务） ↕ AIDL / Binder IPCMcuSdk.aar（Java/Kotlin SDK） ↕ 应用 API收音机 App / 车辆信号 App / 升级 App原架构中 SDK 直接持有 JNI 连接，多个应用进程并发访问时存在串口竞争风险。新架构将 JNI 持有权上移至 SystemService，所有应用统一通过 Binder IPC 访问，实现进程隔离与通信集中管理。二、开发内容补充（一）McuSystemService 开发基于 Android 系统服务机制开发 McuSystemService，通过 ServiceManager.addService() 注册为系统级服务，作为所有上层应用访问 MCU 的唯一入口。主要职责包括：JNI 持有与生命周期管理：由 SystemService 持有并初始化 libserial.so 的 JNI 实例，随系统启动常驻后台，避免多个 App 各自持有串口连接导致冲突；MCU 通信代理：所有发往 MCU 的命令（车辆信号、收音机、升级等）经由 SystemService 序列化后统一下发，避免并发写入冲突；事件广播：MCU 主动上报的数据（ACC/IG 状态、车速、RDS 信息等）由 SystemService 接收后，通过 AIDL 回调接口分发至已注册的客户端；AIDL 接口定义：提供 IMcuService.aidl 接口文件，定义命令发送、回调注册/注销等方法，供 SDK 层及第三方集成使用。（二）McuSdk.aar 优化对原有 Java SDK 进行改造，移除直接 JNI 调用，改为通过 AIDL Binder 与 McuSystemService 通信。SDK 封装以下能力：ServiceConnection 管理：自动处理 bindService 连接、断线重连，对上层透明；同步/异步命令接口：提供 sendCommand()、queryVehicleSignal() 等简洁 API，内部处理 Binder 跨进程调用细节；回调封装：将 AIDL 的 IBinder.DeathRecipient 和回调接口封装为 Listener 模式，供应用层直接注册使用；向后兼容：对外 API 签名保持与原 SDK 一致，已有应用层代码无需修改。三、交付物补充在原合同交付物基础上，新增以下内容：新增交付物说明McuSystemService.apk / 系统内置包可独立安装或预置到系统镜像的服务端 APK更新版 McuSdk.aar移除直接 JNI 依赖，基于 Binder 通信的新版 SDK，集成 aidl《SystemService 集成说明》描述服务注册方式、权限配置、SDK 初始化流程四、技术指标补充在原合同技术指标基础上，新增以下验收标准：多进程隔离：多个 App 同时通过 SDK 访问 MCU 时，数据不混乱，回调正常分发至各自客户端；服务可用性：McuSystemService 异常重启后，SDK 自动重连，上层业务可感知到重连事件；端到端延迟：应用层调用 SDK 到 MCU 收到命令，端到端延迟 ≤ 50ms（不含 MCU 响应时间）；权限控制：AIDL 服务接口设置适当的 Android 权限声明，防止未授权应用访问 MCU。五、责任边界说明本补充条款新增内容的责任边界与主合同保持一致：McuSystemService 及更新版 McuSdk.aar 的开发、测试与交付由乙方负责；SystemService 的系统镜像预置、签名及部署配置由甲方负责；本架构变更不影响 MCU 固件侧协议，串口通信协议仍遵循 MCU-ARM_v2.xlsx 定义，MCU 固件开发维护仍由甲方负责；因甲方系统镜像配置或签名问题导致 SystemService 无法注册的，由甲方负责解决，乙方不承担相应责任。
