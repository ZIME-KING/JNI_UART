### 架构与并发

- 串口独占与线程安全：系统只允许一个串口连接；Native 层实现单例；收音机/车辆/升级等业务共用同一收发通道，保证线程安全，避免数据交叉。
- 异步上报与回调：MCU 主动上报的数据必须通过回调通知 Java 层；回调需运行在指定线程（主线程或后台线程）。

### 协议与链路管理

- 协议严格实现：按 MCU-ARM_v2.xlsx 实现帧格式、序列号、校验和（累加和取反）、建链（Setup/SetupAck）、心跳、ACK、重传。
- 心跳：间隔 ≤3 秒；建链成功后每隔 2 秒发送心跳帧；若连续 3 次心跳无响应，自动重建链路。
- ACK：对需要确认的发送帧阻塞等待 ACK；超时 200ms；重试 3 次；失败返回错误码。
- 断线重连：检测到串口错误或心跳超时后，自动关闭并重新打开串口，重新建链。

### 业务能力

- 车辆信号（Public）：支持 ACC/IG、倒车、车速、电池电压、MCU 版本查询；支持背光亮度设置、功放/天线电源控制、休眠请求；心跳发送维持链路。
- 收音机（Radio）：支持设置波段与频率、SEEK 自动搜索、TA/AF/立体声/本地开关设置；支持频率/信号强度、RDS（PS/PTY/RT）上报并回调。
- 升级（Update）：支持启动升级请求、分包下发升级数据（最大 1024 字节/帧，ACK 重传）、结束升级；升级期间其他业务应暂停或缓存，结束后恢复。

### 交付物

- 提供 Native 源码（C++ 完整工程，CMake 可编译）与 arm64-v8a 预编译 .so；提供 Java SDK（.aar 或 .so + 接口 jar）与 Demo App 源码。
- 提供技术文档（集成指南/API 参考/协议实现对照表/调试说明）与测试报告（功能/压力/异常）。

### 日志与验收

- Hex 日志：可动态开关；写前/读后输出一行完整帧（必要时可截断但保留首尾）；格式包含 len 与 hex 内容。
- 帧解析日志：每解析出完整帧至少输出 FrameType/MsgType/Cmd/序列号/数据长度/校验和是否通过；心跳/ACK 需单独标识。
- 日志级别：必须实现编译期宏控制（如 LOG_LEVEL_DEBUG/INFO）；建议支持系统属性运行时控制（如 persist.carserial.log.level）。
- 性能与安全：DEBUG Hex 日志不得影响串口读写实时性；Release 应移除/条件编译掉 DEBUG；日志不得包含用户隐私信息。

# 1. 项目背景

基于 Realtek RTD1861 芯片的 Android 车载中控主机。硬件方案公司已提供 BSP 层，并开放了与 MCU 通信的串口设备节点 /dev/ttyS7（波特率 460800，8N1）。MCU 与 ARM 之间的通信协议已在文档 MCU-ARM_v2.xlsx、Radio_v2.xlsx、Public_v2.xlsx 中完整定义，包含车辆信号（ACC、车速、倒车等）、收音机（FM/AM 调频、RDS 信息）、系统升级等消息类型。

由于项目时间紧张，我方不采用标准 Android Vehicle HAL 路线，而是采用 “直接读写串口 + JNI 封装” 的快速方案：将串口访问与协议处理封装在 Native 层，生成一个或多个 .so 动态库，供 Android Launcher 及上层 App 通过 Java/Kotlin 调用。该方案需要解决串口独占、多业务（收音机、车辆信号、升级）并发访问、协议完整性（建链、心跳、ACK、重传）等关键问题。

将委托第三方公司完成该底层服务库的开发与交付。

# 2.2 关键要求

串口独占与线程安全：整个系统只有一个串口连接，Native 层必须实现单例模式，所有业务（收音机、车辆、升级）通过同一个串口发送/接收，保证线程安全，避免数据交叉。

协议完整实现：必须严格按照 MCU-ARM_v2.xlsx 实现帧格式、序列号、校验和（累加和取反）、建链（Setup/SetupAck）、心跳（HB，间隔 ≤3 秒）、ACK 机制（超时 200ms，重试 3 次）。

异步上报与回调：MCU 主动上报的数据（如车辆状态变化、收音机频率更新）必须通过回调机制通知 Java 层，回调需运行在指定的线程（例如主线程或后台线程）。

升级功能：支持 MCU 固件升级的数据传输（最大帧长 1024+7），需实现分包接收与确认。

# 2.3 开发语言与环境

Native 层：C++11 或更高版本，使用 CMake 构建。

Java 层：Java/Kotlin，提供 Android Studio 可导入的 .aar 或 .so + 接口 jar。

编译目标：arm64-v8a，Android API Level 31+。

调试支持：提供可动态开关的 hex 日志（logcat），方便与方案公司联调。

# 3.3 升级（Update 类）

根据 MCU-ARM_v2.xlsx update 部分：


| 功能 | 方向 | 说明 |
| --- | --- | --- |
| 启动升级请求 | ARM→MCU | 通知 MCU 准备升级 |
| 下发升级数据 | ARM→MCU | 分包发送，最大 1024 字节/帧，支持 ACK 重传 |
| 结束升级 | ARM→MCU | 升级完成通知 |

注意：升级期间其他业务（收音机、车辆）应暂停或缓存消息，升级结束后恢复。

# 3.4 链路管理（必须）

自动建链：SDK 初始化时自动发送 Setup 帧，等待 SetupAck，超时重试 3 次。

心跳维持：建链成功后启动定时器，每隔 2 秒发送心跳帧（FrameType=0x05），MCU 会回复 ACK（FrameType=0x02）。若连续 3 次心跳无响应，SDK 应自动尝试重建链路。

断线重连：检测到串口错误或心跳超时后，自动关闭串口并重新打开、重新建链。

ACK 处理：对于需要确认的发送帧（如设置频率、锁门等），SDK 应阻塞等待 ACK，超时 200ms，重试 3 次，失败返回错误码。

# 6.2 实现重点

## 6.2.1 设备操作日志

每次 open 设备：记录路径、返回的 fd、errno（如果失败）。

每次 close 设备：记录 fd。

每次 read/write 调用：记录操作类型、请求长度、实际返回长度、errno。

## 6.2.2 原始数据收发日志（Hex 格式）

在 write 之前，将待发送的数据字节以十六进制字符串形式输出，一行完整帧。

在 read 之后，将从串口读到的原始字节以十六进制字符串形式输出（建议每帧单独一行，如长度较大可截断但需保留首尾）。

格式要求：TX len=XX, hex: XX XX XX ...；RX len=YY, hex: YY YY YY ...。

## 6.2.3 协议帧解析日志

每解析出一个完整帧（包括帧头、长度、序列号、帧类型、MsgType、Cmd、数据、校验和），至少输出：

帧类型（FrameType）、MsgType、Cmd、序列号、数据长度、校验和是否通过。

对于心跳帧、ACK 帧，单独输出标识。

## 6.2.4 链路状态日志

建链发起、超时、重试、成功、失败。

心跳发送与接收：每次发送心跳及收到对应 ACK 时输出。

链路断开检测及重连尝试。

## 6.2.5 业务命令日志

发送任何主动命令（如设置频率、搜索、设置背光）时，输出命令名称及参数。

收到异步上报（如车速、倒车、收音机频率）时，输出解析后的业务数据。

## 6.2.6 错误与异常日志

任何系统调用失败，必须输出 strerror(errno) 和 errno 值。

校验和错误、帧长度异常、无效 MsgType/Cmd 等协议异常。

ACK 超时、重试次数达到上限。

# 6.3 日志开关与动态控制

必须实现编译期日志级别宏（如 LOG_LEVEL_DEBUG、LOG_LEVEL_INFO），方便我方在开发阶段开启 DEBUG，量产阶段关闭。

建议实现运行时控制：通过 Android 系统属性（如 persist.carserial.log.level）动态调整日志级别，无需重新编译。示例：

```c
int log_level = __system_property_get("persist.carserial.log.level", value);
if (strcmp(value, "DEBUG") == 0) enable_debug = 1;
```

默认出厂配置为 INFO 级别，DEBUG 级别仅在开发/联调阶段开启。

# 6.4 日志性能与安全要求

DEBUG 级别的 Hex 日志不得影响串口读写实时性（建议使用异步日志缓存或仅在可控频率下输出）。

生产版本（Release 编译）应移除或条件编译掉 DEBUG 级别日志，避免日志刷屏和泄露敏感数据。

日志中不得包含用户隐私信息（如 GPS 坐标、设备唯一标识等），仅保留技术调试数据。

# 6.5 验收时需提供的日志示例

提供一份完整的 logcat 输出文件，覆盖以下场景：

设备上电 → 建链 → 心跳 → 发送收音机调频命令 → 收到频率上报 → 进入休眠 → 唤醒重连。

模拟一次 MCU 升级过程（从请求升级到传输数据到结束）。

模拟一次串口断线（例如拔线）后自动重连的过程。

日志中必须清晰体现上述强制日志点的输出。

# 7. 验收标准

功能完整性：所有协议中我方指定的命令（见第 3 节）均可正常收发，MCU 正确响应。

稳定性：连续运行 48 小时，无内存泄露、崩溃、串口死锁。心跳保持，无异常断链。

并发安全：同时调用收音机和车辆接口（例如搜索电台的同时上报车速），数据不混乱，回调正常。

升级测试：能够成功完成 MCU 固件升级（至少模拟升级流程）。

日志：提供可开关的 hex 日志，方便与方案公司联调。

文档：文档清晰，我方工程师可独立完成集成。
